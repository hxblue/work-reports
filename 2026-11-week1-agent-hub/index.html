01 · 为什么做这件事

大部分人用 Agent，还是聊天的方式。

打开 Codex 或 Claude Code，给它一个任务，盯着它干，干完了检查一下，再给下一个——所有事情的起点都是人自己：人不开这个窗口，什么都不会发生；而一个人能同时盯的事是有限的。

01 · 这次搭中台的出发点 04
常见用法

聊天式：人是起点

每件事都要人先开窗口、下命令，Agent 才会动。

  • 人决定什么时候开始
  • 人全程盯着、随时检查
  • 一个人能同时推进的事有限
这次想做的

领导力思维：信号是起点

把"任务发生"这个起点从人身上拿掉，用各种信号去触发 Agent 工作。

  • 定时、报警、工单等信号自动触发
  • 人只在需要判断时才被叫醒
  • Agent 不必等人下命令才开始

03 · 我的理解 06
AI 提效

做 Agent 提效，我认为要抓住四件事

这些也是我选型和设计中台时的判断依据。

  • 薄中台，厚一线。中台只管调度、权限和记录；效果来自一线把自己的流程交给 Agent。
  • 数据最重要。给 Agent 用的资料要有来源、有时间、有负责人，否则它会照着过期的规则办事。
  • 人更重要了。能流程化的交给 Agent，人负责判断、拍板和沟通，所以关键节点要方便人介入。
  • 企业要的不是演示。要可控、可测、可审计、可运维、可复用、可集成，缺一项就难进真实业务。

04 · 中台是什么

业务里发生的事，按规则交给 Agent

Agent 能自己办完就办完；遇到删数据、重启服务、花钱、对外发消息，先停下来问负责人，选完再接着做。

04 · 企业级要求 10

它怎么满足企业级要求

01
可控
用什么模型、在哪干、有什么权限只由规则决定，Agent 改不了；危险操作必须人工确认，随时能停。
02
可审计
记录只增不改，每一轮为什么触发、谁处理、结果是什么都能查到。
03
可运维
网页工作台看全局；规则写错时自动沿用旧规则并提示，不会把系统搞停。
04
防注入、防失控
工单、报错等外部文字只当资料不当指令；Agent 互相触发超过 8 层自动熔断。
05
可集成
大模型可换；业务系统用 HTTP 或 Webhook 接入；通知支持企业微信、钉钉、飞书。
06
省钱
等人回复时 Agent 不运行；巡检用普通脚本，只有真出问题才调用大模型。

05 · 接入公司业务 11

中台已具备的能力，可以这样用

01
定时巡检
定时检查官网、后台、接口，出问题先让 Agent 查原因，再通知负责人。
02
报错初步排查
系统报错自动交给 Agent，对照代码和日志给出初步结论。
03
定时整理汇总
定时汇总日报、周报、表格数据，生成摘要发给相关的人。
04
工单 / 反馈跟进
新工单进来先分类、查资料、准备回复，需要决定时找人确认。
05
代码交付流水线
提交即触发 Agent 审查，按阻塞 / 建议分级标注，测试通过才合并，发布后核对线上版本——过去靠人逐行看的审查，Agent 先挡掉大部分重复性问题。
06
企业微信通知与确认
需要人拍板时发企业微信消息，负责人点链接选择，不用学新工具。

具体接哪个、怎么接，需要和您及业务同事聊过之后再定。

05 · 企业微信怎么接 12
现在就能用

企业微信群机器人

中台自带这个通道，配置一个群机器人地址就能发消息。

  • 只能发文字和链接
  • 负责人点链接，在网页上做选择
  • 开源项目只在模拟环境验证过，还没在真实企业微信上试
需要时再做

企业微信自建应用

想在企业微信里直接点按钮确认，就建一个自建应用，再开发一个通道插件。

  • 消息里直接点按钮，体验和审批类似
  • 中台支持这种扩展，不用改中台本身
  • 需要企业微信管理员开通应用权限

06 · 风险和条件 13

要正式用起来，需要先想清楚这些

  • 01数据集中的安全风险中台汇集各系统的事件和记录，本身是敏感点。控制访问、保管好密钥，Agent 默认只读，按需逐项放开。
  • 02要放到服务器上现在跑在我的电脑上，关机就停。正式使用需要一台公司服务器 7×24 小时运行。
  • 03用公司的 API Key现在用的是个人账号。用于公司业务应使用 API Key，需要一笔模型预算；巡检类任务费用很低。
  • 04复杂长任务仍不可靠步骤很多的任务大模型仍可能跑偏，先从边界清楚、能人工兜底的场景开始。
  • 05业务数据要先理清给 Agent 的资料要有来源、时间和负责人，需要业务同事配合。

07 · 我适合做什么 14
优点
  • 关注面广，主动了解 AI 各个方向、各家大模型的表现和行业动态。
  • 有部署上线经验：在前公司部署到火山引擎，平时把项目部署在阿里云和 Vercel 上。
  • 动手快，能很快把开源项目用起来、接到实际场景里，这次一周内做出了能用的原型。
不足与应对
  • 对单项技术的底层原理钻研不深，更关注它能做什么、效果怎么样。
  • 应对：优先选成熟的开源方案，不自己造底层。
  • 需要深挖时，向有经验的同事请教，或单独留时间研究。
所以我适合做 FDE：贴近业务，找到能用 AI 提效的环节，选合适的现成工具接进去，部署上线并持续跟进效果。
